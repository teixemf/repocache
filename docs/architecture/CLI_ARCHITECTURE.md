**Owner:** REPOCACHE maintainer  
**Language:** English for command names, help, errors, tests and technical documentation

**Platform scope:** Debian 13 and AlmaLinux 10 only, unless separately approved

No command is considered available without inspection and tests of the exact installed version.

## 2. CLI ownership and product trust boundaries

### 2.1 `repocache` — installed server administration

Manages the server's **authoritative managed repository configuration** and derived NGINX/cache exposure, together with diagnostics, installation, repair and signed application updates. It may invoke a restricted, explicitly installed authorization mechanism for privileged changes. It MUST NOT become an arbitrary root command runner.

### 2.2 `repocache-client` — installed client operations

Discovers and validates local APT/DNF sources, validates the server's published catalog, submits sanitized repository requests, and plans/applies opt-in local source changes. Its four approved entry points remain intact. `repos sync` is **read-only by default**; `--apply` is the only approved client source-mutation opt-in. A server repository becoming active must **not** automatically rewrite any client's package manager sources. Retain verified upstream fallback and recoverable backups.

### 2.3 `repocache-release` — independent maintainer workstation tool

Automates release candidate preparation and evidence retrieval, not release authority. It is not a server or client runtime dependency. Owner-held Ed25519 signing keys and passphrases remain outside GitHub Actions. Signing, draft staging and publishing require distinct, explicitly authorized actions; draft status and acceptance evidence are checked against immutable asset digests. Never auto-merge, auto-sign or auto-publish.

### 2.4 The interactive TUI

This document specifies **noninteractive CLI commands only**. The existing interactive `repocache` entry behavior on a TTY is not redesigned or disabled by implication. A bare executable and the `repocache` TUI startup path must be explicitly reconciled and regression-tested at implementation time. An object invoked without an action shows help and has no side effects.

## 3. Parsing, aliases and command grammar

```text
<program> [GLOBAL_OPTIONS] OBJECT [SUBOBJECT] ACTION [POSITIONAL_TARGETS...] [ACTION_OPTIONS]
<program> OBJECT [SUBOBJECT] ACTION [POSITIONAL_TARGETS...] [ACTION_OPTIONS] [GLOBAL_OPTIONS]
```

Examples of equivalent forms:

```console
repocache --json repos list
repocache repos list --json
repocache repo ls --json

repocache repos remove debian
repocache repo rm debian

repocache-client --json repos list
repocache-client repos list --json
```

Rules:

1. Plural object spellings are canonical. Singular aliases use the identical implementation and return equivalent semantic results; no implicit fuzzy abbreviations or arbitrary prefixes.
2. The action is explicit. `repocache repos` shows help, not a default repository listing; the same holds for other object roots.
3. Identifiers are positional. Multiple IDs are accepted only where the command's documented contract allows a batch.
4. A command's global options are accepted in both approved placements, consistently across all three executables. Command-specific options need not be accepted before the object.
5. Invalid, conflicting or unsupported options fail *before mutation*. `--all` and explicit repository targets are mutually exclusive.
6. Named list filters use typed options (e.g. `--type apt --status active`). Different named criteria narrow the result conjunctively. Unapproved OR/multi-value rules and generic `--filter key=value` are absent.
7. `--help` on any level performs neither writes nor network authentication or probes. Help and completion expose only implemented commands in the installed version; future commands remain in planning documentation.
8. `--dry-run` guarantees no persistent host, REPOCACHE state, remote administrative state, package-source, release, audit or cache mutations. Explicit read-only validation is permitted; outbound probes, if any, must be disclosed.
9. All command-line modes are noninteractive, including failures and non-TTY calls: no automatic `sudo`, credential prompt, hidden confirmation or implicit user input. The interactive TUI is a distinct entry mode.
10. Distinguish `check` (diagnostic state), `validate` (input/config constraints), `verify` (integrity/authenticity), `test` (active probe), `status` (operational state), `stats` (measurement), and `show` (single record).

### 4.1 Managed repositories: authoritative lifecycle

Core examples:

```console
repocache repos list --type apt --status active
repocache repos show debian
repocache repos test debian

# The ID is optional. The complete metadata schema is defined by #18/#95.
repocache repos add --type apt --upstream https://mirror.example.org/debian
repocache repos add debian --type apt --upstream https://mirror.example.org/debian
repocache repos update debian --upstream https://mirror2.example.org/debian
repocache repos enable debian
repocache repos disable debian

repocache repos remove debian
repocache repos remove debian --purge
repocache repos remove debian ubuntu
repocache repos remove --all
repocache repos remove --all --purge --dry-run
```

**Type/security qualification:** The `--upstream` examples illustrate CLI grammar. A valid deployment requires the validated repository layout, metadata signing/trust and upstream authorization required by #18/#28/#95; a URL by itself is not sufficient proof of support or trust. `--type` and further per-distro metadata MUST be fully validated against the implemented schema before any activation.

**Identity:** Omitting `[ID]` allocates a stable unique identifier and returns it. Supplying `[ID]` uses the operator-requested identifier after strict collision, normalization, lookalike and ownership checks. An exact repeated add must not create duplicates; the implementation must compare canonical repository identity/configuration safely, not guess identity from a superficially matching URL. An already-used ID with different configuration fails and directs the operator to `repos update`. IDs MUST survive restart, upgrades and safe reinstallation.

**Enablement and observed exposure:** `enabled` (desired administrative configuration) is not equivalent to `active` (actually validated, correctly exposed and published). The lifecycle engine stages configuration, verifies managed NGINX syntax (`nginx -t` where appropriate), applies controlled reload, verifies actual exposure and then updates discovery atomically. Unverified or failed activation is never advertised as active.

**Remove:** Default removal withdraws managed configuration/exposure and discovery while preserving owned cached bytes. `--purge` additionally deletes only safely attributable cache objects. Purging an absent repository with retained cache requires a protected ownership/identity record and generation-safe matching. Never follow symlinks or remove shared/ambiguous/foreign data. If safety cannot be proved, fail closed; do not turn a retained-cache policy into a guessed filesystem deletion.

**Batch semantics:** Validate command-wide invariants before any mutation. Continue safely independent targets after target-local errors, produce item-by-item results and return a nonzero exit code when any required target fails. An absent target on an idempotent removal is a reported no-op success; real permission/storage errors are not suppressed.

**Later feature:** `repos apply --file FILE [--dry-run]` is a future declarative management path, without committing it to a particular numbered release. It must reuse the same authoritative engine as direct commands.

### 4.2 Derived routes and automatic catalog

```console
repocache routes list
repocache routes show debian
repocache routes check debian

repocache catalog list
repocache catalog show debian
repocache catalog check
```

**No independent route or catalog mutator.** Do not expose `routes add/update/apply/remove`, `catalog publish`, `catalog rebuild`, manual catalog approvals, or another source of truth. Routes are derived from validated managed repository configuration; the versioned catalog is an atomic read-only projection of repositories actually active and enabled. Deleting, disabling, updating or adding a repository reconciles discovery only after safe activation checks. A failure must retain or recover an honest known-working discovery state.

`repocache catalog publish` *does* exist in the v0.4.0-tagged source, but its manually approved allowlist model is intentionally **superseded** in the redesigned interface. Do not repurpose its name for a different silent behavior or preserve a second registry as a compatibility shortcut. Document this as a one-time break before the new interface is released.

### 4.3 Repository Requests and audit

```console
repocache requests list --status pending
repocache requests show 123
repocache requests approve 123
repocache requests reject 123
repocache requests audit list
repocache requests audit verify
```

The server uses **`requests`**, never `submissions` as its primary object. `repocache-client repos submit` is deliberately preserved. Receipt by an unprivileged intake service does not authorize upstream probing, arbitrary URL traversal, configuration edits, NGINX reloads or discovery publication. Protected administrative approval creates an audited decision and triggers a **separate, narrowly authorized activation attempt** when implementation/security gates permit. No second manual catalog approval step is needed; however, approval and activation MUST be independently observable (for example: `pending`, `approved_awaiting_activation`, `activating`, `active`, `activation_failed`). These labels are proposed presentation values; the definitive wire/state schema is owned by #15/#57/#96.

The authoritative decision journal is protected from the intake service and cannot be reconstructed from untrusted queue rows. Failed or unavailable activation is reported accurately, with recovery and no unintended exposure. The optional HTTPS listener remains disabled until code gate #17 and production gate #49 pass; no CLI addition, merge or install automatically enables it.

### 4.4 Cache, diagnostics and service

```console
repocache cache stats
repocache cache purge
repocache cache purge --repo debian
repocache cache purge --repo debian --dry-run

repocache metrics show --period 24h --repo debian --json
repocache logs tail --lines 100
repocache logs follow

repocache config apply --file server.yaml --dry-run
repocache config apply --file server.yaml
repocache service reload --yes
```

- `cache purge` without `--repo` applies only to verified REPOCACHE-owned cache objects. There is no mandatory `--yes`; this never eliminates mandatory OS authorization, ownership proof, preflight or race resistance.
- Per-repository cache measurements must not be fabricated from total filesystem usage. Metrics derived from NGINX logs must disclose incomplete coverage/rotation when relevant, and avoid exposing request secrets.
- `logs tail --json` may return a bounded document once its schema is implemented. The continuous `logs follow` defaults to plain text; **reject `--json` for an unbounded stream** until a distinct, explicitly versioned streaming format is approved.
- `service reload --yes` retains acknowledgement from the existing command contract. `--yes` is not OS authorization. NGINX config validation precedes delegated reload; refuse unmanaged instances and unsafe paths. No global `sudo` privileges or generic privileged subprocess runner.
- `config apply` owns only explicitly declared, validated managed files. It does not overwrite arbitrary operator NGINX configuration, trust stores, certificates, package-manager sources or unrelated service state.

### 4.5 Configuration, provisioning, application updates

Three different change scopes:

```console
repocache config apply --file server.yaml --dry-run
repocache deployment install --file server.yaml
repocache update list
repocache update check
repocache update install 0.5.0
```

- `config apply`: validate and reconcile the owned declarative server configuration through the authoritative safe activation engine.
- `deployment install`: provision a complete managed server on a clean supported host, including approved native packages and service setup, while detecting and respecting foreign ownership. Provide a nonmutating preflight, idempotent repeat behavior and documented rollback limitations.
- `update install VERSION`: install **one exact compatible, authenticated owner-signed application release**, with verified dependency profile and safe generation activation. `update list` remains an approved public command. `update upgrade` is planned, not frozen as an unattended policy: it MUST NOT silently choose unsupported, unsigned, ambiguous or arbitrary newest dependencies. Define compatibility/target-selection and authorization policy before enabling it.
- Same-version repair and rollback must preserve configuration, signed artifact identity, the last known-good generation and versioned persistent state; reject unsafe downgrades and dependency-profile migrations.

```text
repocache-client
├── check
├── repos (alias: repo)
│   ├── list (alias: ls)
│   ├── show ID                  [planned optional detail]
│   ├── submit
│   └── sync [--apply]
```

**Approved anchors (do not rename):**

```console
repocache-client check
repocache-client repos list
repocache-client repos submit --output request.json
repocache-client repos sync
repocache-client repos sync --apply
```

`check` includes repository validation: do **not** reintroduce a separate `check --repos`. Local/offline `repos submit --output FILE` remains supported. Authenticated HTTPS submission is a separate explicit opt-in (the draft work uses `--send` with protected `--token-file`; test and preserve the approved protocol before claiming availability). It must never modify client APT/DNF sources. `repos sync` previews by default; `--apply` is the sole opt-in for actual source changes, after full validation, backup of content and permissions, rollback on error and verified direct upstream fallback. Support `.list`, deb822 `.sources` and AlmaLinux 10 `.repo` within their tested scope. Reject unknown/foreign entries rather than rewriting them.

Client `--server URL` is a program-level selector; like other global options it must work both ahead of the object and after the action. Never log token content, echo credential-bearing URLs, or send credentials on unapproved redirects.

```text
repocache-release
├── environment
│   └── check
├── candidate
│   ├── prepare VERSION
│   ├── sign VERSION
│   ├── stage VERSION
│   ├── status VERSION
│   └── publish VERSION

```

Representative usage:

```console
repocache-release environment check
repocache-release candidate prepare v0.5.0
repocache-release candidate sign v0.5.0 --passphrase-fd 3
repocache-release candidate stage v0.5.0
repocache-release candidate status v0.5.0 --json
```

The grammar intentionally supersedes the **flat command spellings proposed by issue #88**; issue text must be aligned before implementing or claiming acceptance. Its **security and provenance acceptance criteria are unchanged**:

- Environment checks authentic GitHub permissions, key fingerprint and private signer path/ownership without revealing secret material or requiring root.
- Candidate preparation binds exact reviewed Git commit/tag, workflow run/head, dependencies and unsigned asset digests. No execution of unauthenticated downloaded code.
- Signing is a separately requested local step, with passphrase through a protected FD or approved interactive TUI, never arguments, environment variables, committed files or GitHub Secrets.
- `candidate stage` uploads only authenticated exact-matching artifacts into an authorized **Draft Release**, refusing unexpected assets or mutations.
- `candidate status` reports actual PASS/FAIL/NOT VERIFIED evidence, signatures, hashes, outstanding approvals and drift, with no false success.
- `candidate publish` requires a separate owner action and fresh verified acceptance at the exact candidate and asset digests. Never silently tag, sign, stage, publish or merge.
- Persistent resumable records contain only restricted nonsecret metadata; interrupted operations and retries cannot weaken provenance checks.

No release-operator command is presumed implemented by this document.

## 7. Output channels, JSON and human messages

### 7.1 Finite commands

**FROZEN DESIGN:** A finite `--json` invocation emits **exactly one parseable JSON document on stdout**, including when `ok` is false, and returns a nonzero exit status for a required failure. Diagnostic text, if independently necessary, goes to stderr and must not duplicate or corrupt the JSON document. No ANSI/Rich markup, status spinners, logging lines or non-JSON prologues are allowed on JSON stdout.

In normal text mode, results go to stdout and errors/warnings to stderr. A failure does not become a success because the command printed a JSON document. An idempotent no-op may succeed but must be distinguishable from a fresh mutation when reported.

The **minimum semantic fields** to preserve in a versioned JSON implementation are `ok` (boolean), `error.code` (stable symbolic identifier on failure) and `error.message` (redacted, actionable string on failure). A `schema_version` field and per-operation result records are recommended implementation details; their exact normative schema version and fields must be verified by integration tests before the first release of this new contract.

Illustrative JSON *shape* (not proof of implemented field names):

```json
{
  "schema_version": 1,
  "ok": false,
  "error": {
    "code": "REPOSITORY_NOT_FOUND",
    "message": "Repository 'example' not found."
  }
}
```

Illustrative batch outcome:

```json
{
  "schema_version": 1,
  "ok": false,
  "results": [
    {"id": "debian", "status": "removed", "changed": true},
    {"id": "ubuntu", "status": "failed", "changed": false,
      "error": {"code": "PERMISSION_DENIED", "message": "Insufficient authorization."}},
    {"id": "almalinux", "status": "already_absent", "changed": false}
  ]
}
```

### 7.2 Streaming outputs

Do not misrepresent a sequence of JSON lines as a single JSON document. Until a distinct framing contract is approved, unbounded `logs follow` is text-only and refuses `--json` with a usage error; bounded `logs tail --json` is eligible for the normal finite JSON schema. The exact stream structure is not an architecture-blocking decision.

### 7.3 Errors and process return codes

Symbolic error identifiers are stable uppercase/underscore names, not translations of prose; e.g. `REPOSITORY_NOT_FOUND`, `REPOSITORY_CONFLICT`, `INVALID_CONFIG`, `PERMISSION_DENIED`, `UNSAFE_PURGE`, `UPSTREAM_UNAVAILABLE`, `INVALID_RELEASE`, `BUSY`, `PARTIAL_FAILURE`. Names are candidates for the cross-executable error registry, not an indication that all handlers exist.

**Approved invariant:** exit 0 for successful operations, including a safe idempotent no-op; nonzero for required failures and partial batch failures. No numeric code is assigned here for partial success. The maintainer approved uniform categories in principle and explicitly delegated **the final numeric mapping and edge cases to the separate `repocache-client` architecture session**. Once that work is accessible, produce one registry covering all three executables and run compatibility tests against the published v0.4.0 behavior. Do not invent that session's decisions or prematurely freeze 1/2/3/4/5/75 as a normative new map.

Published v0.4.0 provides command-specific meanings (for example updater busy uses 75; client `check` uses distinct nonzero statuses). The redesigned interface may deliberately break some non-mandated old mappings, but this must be documented explicitly and never silently change the already approved client contracts.

## 8. Idempotence, batching and safe mutation

- `repos add ID` repeated with the same validated canonical configuration returns success/no-op; a collision with different configuration fails without modification.
- When ID is omitted, identical repeated intents MUST NOT create duplicate managed repositories or exposure. Ambiguous equivalence fails rather than silently merging dissimilar repository definitions.
- `repos update`, `enable`, `disable`, future declarative `apply` and client `repos sync --apply` converge to the same validated desired state on safe repeat.
- `repos remove ID` when absent returns success/no-op, while preserving genuine permission, tampering, integrity and storage errors.
- `repos remove ID...` continues independent safe targets after a target-specific failure and reports each target. Invocations with global unsafe scope or invalid options fail before mutation.
- `repos remove --all` addresses only managed repositories and cannot be combined with positional IDs; `--purge` has the additional cache ownership constraints.
- `cache purge --repo ID` must remain safe even after the repository configuration was removed, using generation-safe attribution or an explicit refusal when the proof is unavailable.
- Durable changes use bounded locks, atomic writes/replace where appropriate, validated preflight, repeat-safe state transitions and recoverable rollback. Do not claim all multi-step filesystem/network operations are universally atomic.
- A `--dry-run` operation may report that final authorization/reload outcomes cannot be guaranteed without performing the real operation; it must not mislabel a simulated test as a completed mutation.

## 9. Security, authorization and operational requirements

**Least privilege:** execute normally unprivileged reads without root. Privileged changes use reviewed, constrained and explicitly configured delegated operations, scoped to owned resources. No arbitrary shell or `sudo`/Polkit escalation, no interactive password prompts, no broad permissions for the intake service. `--yes` only acknowledges the operator's intended action.

**Input validation:** reject malformed repository IDs, URL/host/path bypasses, Unicode lookalike/collision ambiguities, traversal and symlinks, unapproved redirect/DNS changes, unsupported repository layouts, spoofed or unsigned metadata, out-of-policy release manifests and dangerous filenames. Never let client request data become privileged configuration without separate independent revalidation.

**Transaction boundaries:** repository state is authoritative; NGINX routes and discovery derive from it. Updates must stage and validate, then reload/verify using protected owned paths, then publish the correct active set, with explicit recovery on partial failures. Intake and its storage have no automatic root mutation capability.

**Client safety:** Debian 13 APT and AlmaLinux 10 DNF retain working upstream access to the maximum supported degree, with documented cases where automatic fallback cannot be guaranteed. Back up source bytes and essential metadata; preserve operator-owned files, permissions and SELinux constraints. Never claim native-platform test coverage from synthetic unit fixtures.

**Signed updates:** fail closed on unsigned/incompatible/ambiguous versions and dependency profiles; preserve v0.4.0 immutable signed release semantics and the approved transition requirements from #82/#83/#84. No runtime resolution of arbitrary newest third-party wheels and no use of secret signer credentials on target machines.

**Release and production gates:** no code merge without per-criterion PASS evidence, required CI/reviews and explicit maintainer approval. No live HTTPS request intake without #17 code gate and #49 native production activation gate. No release publication without owner-controlled exact-candidate acceptance, distinct authorization and proof of unchanged assets.

```text
  --dry-run   Preview without persistent mutations
  --json      Produce one JSON result on stdout
  --help      Show contextual help
```

## 11. Compatibility and deprecation

1. **Current design window:** The maintainer explicitly authorized a clean redesign because the application has not entered their production use. This is a deliberate opportunity to replace inconsistent v0.4.0 spellings, not proof that no external user exists.
2. **Preserve mandated anchors:** Keep the four exact client commands and `repocache update list` recognizable; `check` already includes repository validation. Keep an explicit migration table for any other published spellings replaced or removed.
3. **Known deliberate changes:** v0.4.0 `repos info ID` → `repos show ID`; `repocache update --version VERSION` → `repocache update install VERSION`; manual `catalog publish` is replaced by automatic derived publication; `repocache-release` issue #88 flat proposed commands → nested object grammar. `status`, `health`, bare `metrics`, and other current usages need audit before a release claims full CLI migration.
4. **After interface stabilization:** Any later supported command/option removal requires a documented deprecation, stderr warning and continued working behavior across **at least two published stable releases** preceding actual removal. For example, warning in releases N and N+1, earliest removal in N+2. Do not count unreleased tags, RC builds or draft releases as the required stable notices.
5. **Migration correctness:** Document old/new invocation examples and behavior/exit-code changes, including JSON. A deprecated alias preserves its documented functional meaning during the notice window; warnings never pollute JSON stdout.
6. **No invented release dates:** This v1.0 document does not assign the redesigned CLI to software v1.0.0 or to any specific milestone. GitHub issue and PR dependencies govern the approved schedule.
